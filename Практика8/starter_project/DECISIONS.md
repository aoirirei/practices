# Принципиальные решения

1. Статус изменяет только сама модель BusinessTrip через submit, approve, reject, cancel, complete. Публичного setStatus нет. Сначала проверяется исходное состояние, затем аргументы операции, и только после этого меняются поля. Неверный переход даёт IllegalStateException, неверные данные — IllegalArgumentException. При ошибке статус и причина остаются прежними. REJECTED, CANCELLED и COMPLETED — терминальные состояния по перечисленным в условии переходам.

2. Минимальная длина причины варианта 1 равна 10 и хранится только в MIN_REASON_LENGTH. Причина проверяется и сохраняется после strip; длина определяется String.length. Даты и id неизменяемы. Конструктор отклоняет незаполненные обязательные данные и end < start, submit повторно проверяет данные. complete принимает явную дату для воспроизводимых тестов и требует today > end. В консоли complete без параметра использует дату Москвы, complete;date явно включает тестовую дату.

Сервис хранит заявки в памяти по уникальному id, создаёт их, находит по id и фильтрует по статусу. Правила переходов в сервисе не дублируются. В исходной диаграмме было поле Employee без класса и без требования в исходном коде; в итоговой модели оно исключено. Все обязательные данные текущего задания: id, start, end.
